# The leash, and permission prompts answered from a session's tile

11 Nov 2026. One agent's round on track E's second half. `npm run typecheck` clean. `npm test`:
452 passed (37 files; 30 new in `test/leash.test.ts`). `npm run smoke`: 418 passed, 0 failed (36
new under `leash:`, `permission:` and `restart:`).

## What was verified on the real CLI (Claude Code 2.1.322)

Run in a throwaway tmux session, Haiku, `--permission-mode default`, with logging hooks that wait
on a file. Not in the repo; the facts are:

- **`PermissionRequest` exists.** It fires after PreToolUse, only when the CLI would ask. Input:
  `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`,
  `tool_input`, `permission_suggestions`, plus `prompt_id`. **No `tool_use_id`** (PreToolUse has one).
- **The dialog shows while the hook runs.** The two race; whichever answers first wins.
- **Hook answers.** `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`
  closes the dialog and runs the tool. `"behavior":"deny","message":"…"` closes it, and Claude
  reads the message as the tool result ("Denied by PermissionRequest hook" in the terminal). The
  transcript records both as an attachment `hook_permission_decision` with the `toolUseID`.
- **The terminal answers first.**
  - Yes: the tool runs, PostToolUse fires, and **the hook is left running** until its timeout or
    the CLI exits. Its later answer is ignored.
  - No: the hook gets SIGTERM, the turn is interrupted, and no Stop hook fires.
- **`claude agents --json`** reads `status: "waiting", waitingFor: "permission prompt"` while the
  dialog is up, and `busy` straight after a Yes. This is how core sees a Yes quickly.
- **A PermissionRequest hook that times out** is SIGTERMed and the dialog stays up.
- **PreToolUse holds the call** ("running PreToolUse hook" in the spinner) for as long as it runs.
  Esc during the hold SIGTERMs the hook and interrupts. **A PreToolUse hook that times out lets
  the call through** to the normal permission flow, so the leash refuses a call itself before its
  own timeout.
- The `permission_prompt` Notification fires about six seconds after the dialog, as documented.

The docs (code.claude.com/docs/en/hooks) agree on all of this, except that they do not say that
the hook outlives a Yes in the terminal.

## What exists

- **The leash.** ⏸ on a session's tile head and on the center head. Pausing writes
  `<profile>/leash/<id>.paused`. The PreToolUse hook (`<profile>/leash.sh`, written by `hooks.ts`)
  checks for that file and exits at once when it is not there. **An unpaused session never calls
  core for a tool call.** When the file is there, the hook POSTs `/ask/pretool` and waits. The
  card shows the held call (tool, description, command) with Resume and Refuse. Resume lets it run.
  Refuse denies it with a reason Claude reads, and the session stays paused, so the next call is
  held too. ▶ resumes.
- **Permission prompts.** The PermissionRequest hook (`<profile>/ask.sh`) POSTs `/ask/permission`
  and waits. The tile (or the center head, when the session is focused) shows "Wants to use", the
  tool, its label and its input as text, with Allow and Deny. The status mark goes to "needs you"
  (`blocked`, attention) while any prompt is open. Allow answers `behavior: allow`. Deny answers
  `behavior: deny` with "The user denied this tool call. Do not retry it; ask them what to do
  instead." The terminal's own dialog stays, and either answers.
- **How core learns the terminal answered**, so the buttons go:
  - a No or Esc kills the hook, its request closes, and core drops the prompt;
  - the fleet poll leaves "waiting for permission prompt" (a Yes; within the 1.5 s poll);
  - PostToolUse / PostToolUseFailure post `/hook/ran` only while `<id>.asking` exists, and core
    drops the prompt with the same tool and input (several prompts at once);
  - Stop or UserPromptSubmit drops every open prompt of that session.
  A click that comes too late finds nothing (`answerPermission` returns false).
- **Failure.**
  - Core quitting or restarting: `Door.stop` closes held connections without answering. Both
    scripts treat "no connection" (000) and 503 (core starting) as "try again in a second".
    `leash.sh` keeps trying while the pause file stands, so the next core holds the call again
    (smoke restarts core with a call held). `ask.sh` tries for 30 s; meanwhile the terminal's
    dialog still works.
  - The pause survives a restart (it is a file). At start, core removes the files of sessions it
    no longer has, and every `.asking` file.
  - A call held for an hour (`HOLD_MAX_S`) is refused by `leash.sh` itself with "paused over an
    hour ago…". The hooks' timeout is a minute longer, so the CLI never times them out first.
  - Each script runs curl in the background and waits on it, so the CLI's SIGTERM reaches curl
    and core sees the hang-up.
- **Security.** `/ask/*` takes only a session's token, and the payload's `session_id` must be that
  session's: anything else gets an empty answer at once (smoke: outside token, another session's
  id, a browser Origin). Pause, resume, refuse and answer are IPC handlers for core's window only.
  `workshop.sessions` for tiles lists named fields, never `leash` (smoke checks the keys). A tile
  has no `window.core`.

## Not verified

- The whole route with a real Claude in workshop. Every piece was checked against 2.1.322 by
  hand, and the scripts were run for real in tests, but no real session has been paused or
  answered from a tile in the app. `WORKSHOP_REAL_CLAUDE=1` smoke does not cover it.
- Several prompts open at once (parallel tool calls). Core keeps a list and the card shows the
  first "and N more", but how the CLI queues those dialogs and their hooks was not seen.
- Subagents' tool calls go through the same PreToolUse, so pausing a session holds its subagents'
  calls too (deck verified that the payload carries `agent_id`). A per-subagent leash is the
  wolfpack's.
- Permission prompts of a subagent, and auto mode (where prompts are rare and PermissionRequest
  only fires when it would still ask).

## Decisions for Colin

- **A pause outlives core.** Quit the app with a session paused and its next tool call waits
  (up to an hour, then it is refused) until the app is back and you resume. The other way is to
  drop pauses when core quits.
- **Refuse keeps the pause.** It refuses the held call and the session stays paused. The other
  way: refuse and carry on.
- **Allow is "Yes, once".** The terminal's "always allow" and "switch to auto mode" stay in the
  terminal.
- **A held call is not "needs you".** The Knot keeps the session's status while it is paused;
  only a permission prompt turns it to needs you.
- The fix in this round's smoke commit: HEAD's Wikipedia "Today" commit (aa62488) dropped
  `.wiki-text .wiki-title`, so `npm run smoke` on main stops at "the picture of the day" before
  reaching sessions. Smoke now waits for `.wiki-caption`.
