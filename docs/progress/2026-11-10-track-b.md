## What was built, file by file

- `src/shared/manifest.ts`: `backend` is a top-level key, `{ "entry": "backend.mjs", "ops": [...],
  "timeoutMs"?: n }`. `entry` is a relative `.mjs` path inside the folder; `ops` follow the door's
  rules (one `checkOps` now checks both: 1 to 32 lowercase words, none twice); `timeoutMs` 100 to
  120,000, default 10,000; any other key is refused (so a `background` flag is an error, not a
  silent no-op). `checkManifest(raw, { dev, builtin })`: without `builtin` a backend is refused
  with `TRUSTED_ONLY`, which now lives here (tile-check re-exports it), so install, `tile check`,
  `readTile` and the validator say the same sentence. `permissions.backend` in tile.json is always
  refused; core SETS `permissions.backend = true` on a parsed manifest that declares a backend, so
  the words, the install comparison and the bridge's hello see it like any permission.
  `BRIDGE_VERSION` is `1.2.0` (the overlay was 1.1). The fixture says `"workshop": "^1.2"`.
- `src/main/tile-check.ts`: passes `builtin` to the validator, and for a built-in backend checks
  the program exists inside the folder (real path). The refusals for everything else are as
  track A wrote them (`wantsBackend`: a top-level `backend`, `permissions.backend`, or a
  `backend.mjs` file).
- `src/main/tiles.ts`: `readTile` refuses as before for every source but `core`; for `core` it
  resolves the backend's real path inside the folder into `Tile.backend` (null for every other
  tile). A dev folder standing in for a built-in id is `dev`, so it never has one.
- `src/main/backend-protocol.ts` (new, no electron): the wire. `{ type: 'call', id, op, body }`
  and `{ type: 'sessions', sessions: [{ id, name, folder, root, status }] }` to the backend; `{ type:
  'ready', ops }`, `{ type: 'reply', id, ok, result | error }` and `{ type: 'fatal', error }` back.
  `plainJson` (JSON only, body 1 MB, result 8 MB), `readFromBackend`, `restartDelay` (1 s, 3 s,
  10 s, then give up; a run of 60 s resets the count), `backendEnv`, and `createKit`, the
  backend's side without the process.
- `src/main/backend-host.ts` (new, a second main entry in `electron.vite.config.ts`, built to
  `out/main/backend-host.js`): what the utility process runs. It plugs the kit into
  `process.parentPort`, imports the tile's `backend.mjs` and calls its default export with
  `{ handle, sessions, onSessions }`, then says ready. A load error or an uncaught exception is
  sent as `fatal` and the process exits 1. This is the helper for authors: nothing to import,
  no dependency, and the protocol stays core's.
- `src/main/backend.ts` (new, no electron import): `Backends`. `sync(wanted)` starts and stops;
  `call(id, op, body)` refuses an undeclared op and a non-JSON body before the backend hears of
  them, holds calls while it starts or restarts, and times each out at the manifest's
  `timeoutMs`; `setSessions` sends the list to every running backend (and each new one gets it
  on ready, before any call). A crash fails the calls already sent, keeps the ones waiting, and
  restarts with the backoff; after the fourth quick death it is `failed`, every call rejects with
  why, and only turning the tile off and on tries again. `status(id)` is `{ state, error? }`
  (`starting | running | restarting | failed | stopped`), pushed to the tile's pages on every
  change. `utilitySpawn` is the real spawner: `utilityProcess.fork(backend-host.js, [program],
  { env, cwd: tile folder, stdio: 'pipe', serviceName: 'workshop backend: <id>' })`, stdout and
  stderr appended to `<profile>/logs/backend-<id>.log` (mode 0600, moved to `.log.1` past 1 MB at
  a start), with a line at every start and exit.
- `src/main/index.ts`: one `Backends`; `syncBackends()` wants every registry tile that is
  `source: 'core'`, has a backend, and is on in `settings.column` (its first instance not in
  `off`, or any extra instance on; no column yet reads as on). It runs after start, after every
  `setColumn` write, and when a dev tile is loaded or forgotten. `pushSessions` also feeds
  `backends.setSessions` (every backend hears of every session, whatever its tile's permissions:
  folders, never tokens). Quit (`before-quit`, and the smoke's exit) calls `stopAll`. The bridge:
  `CH.backendCall` and `CH.backendStatus`, behind `need(e)` (the same sender, top frame and
  origin check as every other call) plus "this tile is built in and has a backend". The hello
  carries `backendOps`. Smoke only: `test/fixtures/trusted` is loaded as a `core` source
  (`SMOKE_BUILTINS`), and restarts come after 100, 200, 300 ms.
- `src/shared/ipc.ts`: `backendCall`, `backendStatus`, `backendStatusChanged`; `TileHello.backendOps`.
- `src/preload/tile.ts`: `workshop.backend` exists only when the manifest declares one:
  `call(op, body)` (an op not in `backendOps` rejects in the page; main checks again),
  `status()`, `onStatus(fn)`.
- `src/shared/permissions.ts`: `FULL_ACCESS`, "run its own program with full access to this

## The environment, and why

A backend's environment is built from an allowlist, not from core's: `PATH`, `HOME`, `USER`,
`LOGNAME`, `SHELL`, `TMPDIR`, `LANG` (default `en_US.UTF-8`), `LC_ALL`, `LC_CTYPE`,
`SSH_AUTH_SOCK`, `__CF_USER_TEXT_ENCODING`, taken from `shellEnv()` (main/env.ts), so `PATH` is
the login shell's and a Homebrew `git` or `gh` is found as in Terminal. HOME finds `~/.gitconfig`
and gh's `~/.config/gh` (gh's own token lives in the keychain or that file, not in env);
`SSH_AUTH_SOCK` lets `git fetch` / `push` over ssh use the agent. Left out on purpose: anything
`WORKSHOP_*` (core itself may be running inside a session, with that session's `WORKSHOP_AUTH`),
`GH_TOKEN` / `GITHUB_TOKEN` and every other key the user exported for something else,
`NODE_OPTIONS`, `ELECTRON_*`. Chromium adds `MACH_PORT_RENDEZVOUS_PEER_VALDATION` to every child
on macOS; that one is not ours to remove. If a git tile turns out to need `GH_TOKEN` (a user who
only authenticates gh that way), it is one line in `BACKEND_ENV`, but it is a decision.

## Not done, or not verified

- **No real tile has a backend yet.** Only the fixture exercises it; Git (track C), Spotify and
  PS2 are the first real users. Nothing here ran `git` or `gh` from a backend.
- **A packaged app**: `out/main/backend-host.js` is found as `join(__dirname, 'backend-host.js')`,
  which holds for `out/` as built. No packaging exists yet to check it in an asar.
- **ES modules in the utility process** are used as Electron 44 ships them (the host is CJS and
  `import()`s the tile's `.mjs`); a `backend.mjs` that imports a sibling module works by Node's
  rules but only the single-file fixture was run.
- **The backend's own output** is only in the log file; nothing in the window shows it. A failed
  backend is told to its page (`status()`, `onStatus`), which must show it; core draws nothing.
- **A body or answer near the caps** (1 MB in, 8 MB out) was not measured over IPC.
- **Turning a tile off** is read from `settings.column`. The smoke changes the column through
  `window.core.setColumn` directly, so the window's own idea of the column is not updated in that
  run; a person's Turn off in the menu goes through the same `setColumn`.
- **A timed-out call keeps running** in the backend; core only stops waiting. There is no cancel.
- The old `install.ts` and `tile-index.ts` refusals were left as they were (they still pass, and
  share `TRUSTED_ONLY`; the index's own sentence for `permissions.backend` is unchanged).

## Decisions Colin should know about

- **`backend` is a top-level key**, not under `permissions` (plan's shape). Core mirrors it as
  `permissions.backend: true` on the parsed manifest so it shows and compares like a permission;
  a tile that writes `permissions.backend` itself is refused.
- **Restart policy**: 1 s, 3 s, 10 s, then give up; a run that lasted a minute starts the count
  again. Off and on is the only retry after giving up.
- **Every backend sees every session** (id, name, folder, root), regardless of a `sessions`
  permission: the plan says it is told which folders exist, and the git tile needs all of them.
- **Caps**: request body 1 MB, answer 8 MB, timeout default 10 s and at most 120 s (as the
  door). Git's slow ops (fetch, rebase) may want the 120 s or a "start, then poll" pair of ops.
- **The bridge is 1.2.0.** A tile built for `^1.1` still loads; a backend tile should say `^1.2`.
- **The env allowlist** above (no `GH_TOKEN`).

## Later still: `started` and `active`, commit records, and events to the page

For the Git tile's History tab (`2026-11-10-history.md`):

- A backend's session also carries `started` (when core started it, ms) and `active` (when core
  last heard a hook from it, ms, or null). Seven fields now; `test/backend.test.ts` and the
  smoke's backend check expect them.
- A new message to the backend, `{ type: 'commits', commits: [{ sha, session, name, at }] }`,
  sent after `sessions` when a backend is ready and again whenever core records a commit a session
  made (`src/main/commits.ts`). The kit has `commits()` and `onCommits(fn)`.
- A new message from the backend, `{ type: 'event', name, data }`: `kit.emit(name, data)` (name
  1–32 of a-z, 0-9, -; data plain JSON, 64 KB at most, checked on both sides). Core hands it to
  every page of that tile as `workshop.backend.onEvent(fn)` → `fn({ name, data })`. It is a nudge
  ("look again"), not a channel for results: the page still asks with `call`. Built-in tiles only,
  like the rest of `workshop.backend`; no bridge version change.
