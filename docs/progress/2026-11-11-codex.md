# Codex sessions beside Claude Code sessions (plan, 11 Nov 2026)

**Decision (Colin, 11 Nov 2026):** workshop runs OpenAI's Codex CLI as a second kind of session,
before any launch. The pitch: Claude Code and Codex in one window, each on your own plan. We do
not build our own agent: Claude Code's source is not published (its repo's LICENSE.md: "All
rights reserved"), Claude subscriptions are for Anthropic's own apps, and each model is tuned to
its own harness. Ground rule 4 holds for both CLIs: unchanged binary, their own extension points,
never their credentials.

Source read: `openai/codex` main at `e58bf8f` (unreleased; workspace version 0.0.0), paths under
`codex-rs/`. **Every claim below must be checked again on the release we install** (phase 0).

## What Codex gives us, against what workshop uses from Claude Code

| Workshop needs | Claude Code | Codex |
|---|---|---|
| Our session id up front | `--session-id <uuid>` | None. Learnt from `thread/started` on the app-server (or the rollout's `session_meta`) |
| Settings merged over the user's | `--settings <file>` | `-c key=value` (TOML), a session layer over the user's `~/.codex/config.toml` |
| Busy / idle / needs you | `claude agents --json` poll + hooks | App-server `thread/status/changed`: `Idle`, `Active{WaitingOnApproval…}`, `SystemError` |
| Answer a permission prompt from a tile, terminal still able to | PermissionRequest hook, held beside the dialog | App-server approval requests go to **every** connected client; first answer wins, the rest get `serverRequest/resolved`. (Codex's PermissionRequest hook runs *before* its dialog, `core/src/tools/approvals.rs:598`, so holding it would hide the terminal's choice: not usable for this.) |
| The conversation in a tile | `~/.claude/projects/<cwd>/<id>.jsonl` | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`; human prompts are their own item type |
| Usage meters | statusLine JSON | `token_count` events: tokens, context window, `rate_limits.primary/secondary` (`used_percent`, `window_minutes`, `resets_at`). **No dollars**: cost needs our own price table, or shows tokens |
| Which session made a commit | PostToolUse on Bash | `CommandExecution` items on the app-server (no hook needed) |
| Subagents (wolfpack) | SubagentStart/Stop, `subagents/` folder | Child threads with `parent_thread_id`, each its own rollout; SubagentStart/Stop hooks too |
| Tile skills | `--plugin-dir` per tile | No per-run plugin dir. Skills live in roots the user or repo owns. Instead: **the door as an MCP server** (`-c mcp_servers.workshop…`), each tile's ops a tool |
| Env for the door (`WORKSHOP_AUTH`, `WORKSHOP_TILE`) | the pane's env | The process that runs tools: the app-server's env, or `-c shell_environment_policy.set.KEY=VAL` |
| Theme follows the app | `theme` in `--settings` | Follows the terminal's real background (asks with OSC 11): tmux must answer it right |
| Sign-in | user's own `claude` login | user's own `codex login` (ChatGPT plan or API key); `auth.json` / keychain never touched |

Codex hooks exist (the same event names as Claude Code's) but a session-layer hook runs only once
its hash is marked trusted in `hooks.state`, an internal format, or with
`--dangerously-bypass-hook-trust`, which also runs the user's untrusted hooks. **Plan: no Codex
hooks at all.** The app-server tells us everything the hooks would.

## The shape: one app-server per Codex session, inside that session's tmux

The Codex TUI is itself an app-server client. By default it attaches to a shared daemon, but
`--remote unix://<path>` points it at any app-server, and several clients can follow one thread.
So a Codex session is:

```
tmux session ws-<id> (core's private socket, as today)
  window 0: codex --remote unix://<profile>/codex/<id>.sock -C <cwd> [-m …] [-a …] [-s …]  ← the pane we attach
  window 1: env WORKSHOP_AUTH=… codex app-server --listen unix://<profile>/codex/<id>.sock -c …
core (main): a JSON-RPC client on the same socket: status, approvals, items, token counts
```

Why per session, in its tmux:
- **It outlives core**, as sessions must. A server that core spawned would die with the app and
  take the TUI with it.
- **Park / kill stay one-to-one**: killing `ws-<id>` ends both.
- **The env is the session's own**: tools run in the server, so its `WORKSHOP_AUTH` is that
  session's token. One shared server could not tell sessions apart.
- Resume after a reboot: start the server again, then `codex resume <thread id> --remote …`.

## Phase 3: what the next session needs

Parity with what Claude Code sessions have. Each item: what is known, what to verify first.

1. **Approvals from the tile: built (11 Nov 2026).** `CodexLink` keeps each approval request of
   its own thread by id (`codexAsk` in `src/shared/codex.ts`: a command unwrapped from
   `zsh -lc`, whole; a file change's paths and diffs from the `fileChange` item seen before the
   request; a network approval names the host) and hands it to the leash as an ask
   (`Leash.offer`: the same list, card and IPC as Claude's PermissionRequest, answered through a
   callback instead of a held hook). Allow is `accept`, Deny `decline` (the turn goes on); only a
   click sends one (`CodexLink.answer`, the one reply core ever sends to a server request). An ask
   is dropped on `serverRequest/resolved`, on the status leaving `waitingOnApproval` once seen in
   it, on `turn/completed`, and when the socket closes (a request belongs to its connection).
   `item/permissions/requestApproval` answers with a granted profile, not a yes: shown with
   "Answer in the terminal" and no buttons (`terminal` on the ask; `answer` refuses it).
   Everything else (another thread's request, `item/tool/requestUserInput`, elicitations, tool
   calls, token refreshes) is neither shown nor answered. **Checked against the real 0.167.1**
   (one prompt, three escalated `touch`es under read-only): core's Allow closed the TUI's dialog
   and the command ran; `y` in the TUI dropped core's card at once (`serverRequest/resolved`) with
   nothing sent; `turn/interrupt` during the third resolved it and the turn ended. The real
   request's `reason` is the model's own sentence ("May I create a.txt…"), shown as the label.
   **Found on the way**, for items 2 and 3:
   - `thread/resume` with `approvalPolicy` / `sandbox` on a **running** thread ignores them (it
     answered `on-request` / read-only after asking for `untrusted`); only `turn/start` changes a
     live thread's policy, and that is a model turn. The protocol's `AskForApproval` does take
     `untrusted` (the CLI's `-a` does not).
   - `turn/interrupt { threadId, turnId }` from a second client works (the turn id from
     `thread/turns/list`, newest first): the TUI shows "Conversation interrupted".
   - The model on this account (`gpt-6-luna`) runs commands through Codex's code-mode `exec` tool
     (JavaScript calling `tools.exec_command`). Commands that ran **sandboxed** that way gave **no
     `commandExecution` item** at all (nor a line in the TUI); escalated ones did (`exec-<uuid>`
     ids, `command` as an argv array in the rollout, a string on the socket). So a session tile
     can miss a Codex session's sandboxed commands, and commits made by one may not be seen.
2. **Pause: Stop instead, built (11 Nov 2026).** The three options, tried on the real 0.167.1:
   holding approvals only adds nothing (a call that needs one already waits on you, the rest run
   on); `thread/resume` with `approvalPolicy` / `sandbox` on a running thread ignores them; and
   `turn/interrupt` works. **Colin chose a Stop button** (11 Nov 2026): ■ on a Codex session's
   heads in ⏸'s place while a turn runs (`StopButton` in `Leash.tsx`; two clicks, the first arms
   it for 3 s), sent as the leash IPC's `stop` (a Codex session refuses `pause` / `resume` /
   `refuse`), `CodexLink.interrupt()`: `turn/interrupt` for the turn core saw start
   (`turn/started`), else the newest `inProgress` one from `thread/turns/list` (a link that joined
   mid-turn). Checked with core's own code on the real CLI, with no model turn: a
   `thread/shellCommand` (`sleep 30`, as `!sleep 30` in the TUI) runs as a turn; interrupted, the
   TUI showed "command aborted by user" and "Conversation interrupted", the session idle at once.
   Re-check a real hold on later releases (overrides on a running thread, or hooks).
3. **Commits: built (11 Nov 2026).** The recorder takes a neutral `ShellCall` (`command, cwd,
   durationMs, saidSha?, endedAt?`): `claudeShellCall` from a PostToolUse payload,
   `codexShellCall` from a `commandExecution` item once `completed` or `failed` (the command
   unwrapped from `zsh -lc '…'`, which `isCommitCommand` needs). `CodexLink` hands every item
   that completes to `itemDone` once, live, and at each `turn/completed` reads that turn's items
   back (`thread/items/list` with `turnId`) for any the server stored but did not send. Seen
   once on 0.167.1: a thread's first turn (a shell command) reached no subscriber, though the
   server kept the item; on a second fresh thread it arrived live, so it is a race. A late item
   is judged at its own `completedAtMs`, not now. The window is the longer of the item's
   `durationMs` and the time since core saw it start (`item/started`, or `startedAtMs` read
   back): a model's command reported `durationMs: 0` (`source: "unifiedExecStartup"`).
   **Checked against the real 0.167.1:** a `thread/shellCommand` `git commit` (no model) and one
   prompt ("Make an empty git commit here with the message hi") under `workspace`: Codex
   protects `.git`, so the model's commit asked to escalate (an approval, accepted), ran as a
   `commandExecution` item, and core recorded its sha for the session. So the gap found at
   item 1 (sandboxed code-mode commands give no item) does not hide commits; it still leaves such
   commands off the session tile.
4. **The wolfpack: built (11 Nov 2026).** `src/main/codex-pack.ts`, owned and fed by the link;
   pure rules `codexChild`, `codexActivity`, `codexAgentTask`, `codexKillLine` in
   `src/shared/codex.ts`. **Seen on the real 0.167.1** (a raw probe, then core's code, three
   prompts that spawned a subagent):
   - The parent records each subagent as `subAgentActivity` items (`kind: started | interacted |
     interrupted | completed`, `agentThreadId`, `agentPath: "/root/ok_agent"`, `model`); its
     `wait` is a `collabAgentToolCall`. No `spawnAgent` item was seen.
   - The child thread: `parentThreadId`, `agentNickname` ("Beauvoir", "Sagan", "Rawls"),
     `source.subAgent.thread_spawn { parent_thread_id, depth, agent_path }`. Its items are its
     own work and words; its brief is not among them.
   - No `thread/started` reached a second client for a child, but the child's events did, with no
     subscription to it (they follow the parent's subscribers). `thread/resume` on a child just
     spawned failed; later it worked. Several subscriptions on one connection are fine.
   - A server started fresh loaded an old thread from disk (`thread/loaded/list`): `pickThread`'s
     folder test is what keeps core on the session's own.
   So a subagent is found from a `started` activity (or a notification from a thread core does not
   know, read once with `thread/read`), subscribed with retries, and read back
   (`thread/items/list`) when found and at each of its turns' end; at join only one still running
   is taken up. Its conversation is `agent:<thread id>` (the same store and ChatView as a Claude
   subagent's), its approvals are the session's asks (per-thread drop rules), its commands go to
   commit attribution. It ends on `completed` / `interrupted` activity, its turn's end or
   `thread/closed`; `interacted` or a new turn revives it. No pause (the pack hides it for
   `cli: 'codex'`). **Kill**, as a Claude subagent's: the tile goes and core stops following it,
   its running turn is interrupted, and the parent is told in one typed line (`codexKillLine`,
   pasted into the TUI). The interrupt alone was not enough on the real CLI: the parent was not
   told, its `wait` timed out, and the subagent was set going again on a new turn. Pasting the
   line into the TUI made the parent interrupt the subagent with its own tool (an `interrupted`
   activity) and finish. Both halves were checked on the real CLI with core's code; not yet the
   two together in one run.
5. **Tiles from a Codex session** (the door): Codex has no `--plugin-dir`. Plan: an MCP server

   as trust) that lists each on tile's door ops as tools and calls `/tile/<id>` with the session's
   `WORKSHOP_AUTH`; skills' words go in tool descriptions. Also the preview pane's `doc`.
6. Later (phase 4): the top bar's windows for a Codex plan (`account/rateLimits/updated`:

## Risks

- The remote / app-server contract is newer than the TUI and parts are marked experimental. Pin
  the minimum Codex version we support and check it at launch; a mismatch says so in the launcher.
- Codex moves weekly, as Claude Code does. The adapter must fail soft: a session whose server
  will not talk to us is still a working terminal, shown as status unknown.
- Cost in dollars is ours to compute for Codex; until a price table exists, show tokens.
